# ADR-0003: SQLite با درایور libsql

**وضعیت:** پذیرفته

## زمینه

انتخاب دیتابیس با درخواست صریح صاحب پروژه SQLite است. اما SQLite در Node سه درایور دارد
و انتخاب اشتباه، درد استقرار می‌سازد.

محیط توسعه: ویندوز. محیط production: لینوکس.

## گزینه‌ها

۱. `better-sqlite3` — ماژول نیتیو، API همگام، سریع‌ترین
۲. `@libsql/client` — API نامتقارن، بدون کامپایل نیتیو، پشتیبانی از فایل و ریموت
۳. `node:sqlite` — درون خود Node، اما هنوز در حال تثبیت

## تصمیم

`@libsql/client` با آدرس `file:./data/haft.db` و Drizzle ORM.

## دلیل

- `better-sqlite3` ماژول نیتیو است. بیلد روی ویندوز و اجرا روی لینوکس نیاز به rebuild
  دارد و در نصب هم به ابزار بیلد وابسته است. برای این پروژه ریسک بی‌دلیلی است.
- `@libsql/client` باینری از پیش ساخته دارد و روی هر دو سیستم بی‌دردسر نصب می‌شود.
- مسیر خروج باز می‌ماند: اگر روزی حجم داده یا نیاز به دسترسی همزمان بالا رفت،
  با تغییر `DATABASE_URL` می‌توان به دیتابیس ریموت رفت، بدون تغییر یک خط کد کوئری.
- تفاوت عملی API فقط این است که کوئری‌ها `Promise` برمی‌گردانند — که در Server Action
  اصلاً هزینه‌ای نیست.

## تنظیمات اجباری اتصال

```sql
PRAGMA foreign_keys = ON;   -- در SQLite پیش‌فرض خاموش است
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
```

بند `foreign_keys` مهم‌ترین است: بدون آن SQLite کلید خارجی را نادیده می‌گیرد و
داده ناسازگار بی‌صدا ذخیره می‌شود.

## پیامدها

آسان‌تر: نصب، استقرار، بکاپ (یک فایل)، هزینه عملیاتی صفر.

سخت‌تر: SQLite تک‌نویسنده است. تراکنش‌ها باید کوتاه بمانند. اگر بار نوشتن
به‌طور جدی بالا رفت، مهاجرت به PostgreSQL لازم می‌شود — که چون همه دسترسی داده
از `repo/` می‌گذرد و Drizzle هر دو را پشتیبانی می‌کند، هزینه‌اش محدود است.
